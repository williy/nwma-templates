# NWMA Templates: IT資産価値管理方式 (Net Worth Management Architecture) v2026.6

> **「思想（A）が構造（B）を支配し、検証（C）が統治を証明する」**

NWMAは、属人化した設計判断を「工学的な資産」へと変換し、ITシステムを「管理負債」ではなく、継続的に価値を生む「IT資産」として運用するための、自己統治型設計フレームワークです。

## 1. 核心となる設計思想：プロフェッショナル・ガバナンス
NWMA v2026.6 では、実務における「設計レビューで殴り勝てる」強度を確保するため、以下の三軸を最優先事項として定義しています。

* **主権の確立 (Ownership)**: 資産の主権（Owner）を明確にし、代行者（Architect/Builder）の責任境界を物理的に隔離する。
* **例外の統治 (Exception Governance)**: 現場の例外を「野良設定」にせず、有効期限付きポリシーとして管理下に置く。
* **強制執行 (Enforcement)**: 試験の失敗を「異常」と定義し、IaCによる即時の自律復旧（Self-Correction）を義務付ける。



## 2. アーキテクチャの階層定義

* **NWMA (Constitution / 設計憲法)**: A/B/Cシートの整合性を司る最上位レイヤー。
* **IWMA (Foundation / 基盤層)**: インフラ基盤。Terraform等を用い、Asset/Vesselの物理境界を定義する。
* **PWMA (Platform / 執行層)**: プラットフォーム。Ansible/K8s等を用い、構成ドリフトを根絶し「あるべき状態」を執行する。
* **Nexus (Enforcer / 自動執行アプリ)**: 三者対話（CXO/User/Engineer）から設計意図（Why）を抽出し、ガバナンスをリアルタイム監視するAIエンジン。

## 3. リソースの定義と保護原則

* **永続資産 (Asset)**: データベース等のデータ層。削除保護（Deletion Protection）により「不滅性」を担保。
* **計算資源 (Vessel)**: ランタイム等の実行層。ステートレスであり、SLOに基づき「置換可能性」を担保。
* **制御平面 (Control)**: 鍵・権限・状態(State)。物理隔離により「統治権」を担保。

## 4. 管理シート：A/B/C Sheets (v2026.6 Professional)

設計から検証までを一つの「ユニバーサル識別子（A-No）」で貫通させ、完全なトレーサビリティを確保します。

| シート名 | 役割 | 重点記載項目 (v2026.6) |
| :--- | :--- | :--- |
| **A-Sheet (Intent)** | 設計ポリシーの定義 | **責任境界、例外ポリシー、Fail時アクション** |
| **B-Sheet (Structure)** | 構成定義の正本 | **設計判断理由 (Why)**、構成パラメータ、A-No紐付け |
| **C-Sheet (Evidence)** | 統治の物理的証明 | **強制執行ドリル、合格基準(Pass/Fail)、是正処置** |

## 5. ディレクトリ構造

```text
nwma-templates/
├── A-Sheets/           # 要件定義・統治ポリシーの記録 (A-No 識別子)
├── B-Sheets/           # 構成定義と物理実装 (B-No リソース定義)
│    ├── IWMA/           # インフラ基盤定義（Terraform等）
│    └── PWMA/           # プラットフォーム構成（Ansible等）
├── C-Sheets/           # 強制執行ドリル・検証試験 (C-No 是正処置)
├── chronicle/          # 意思決定履歴（設計判断の文脈保存）
├── manifesto/          # NWMA基本理念・ガバナンス憲章 (v2026.6)
├── nexus_app/          # [NEW] 三者対話・自動統治 Web アプリケーション
└── templates/          # A/B/Cシート v2026.6 最新テンプレート
```

## 6. NWMA が提唱する「殴り勝てる設計」の 5 大原則

### 1. 設計書の「死文化」への挑戦
ドキュメントを「説明資料」ではなく、運用フェーズで実態と同期し続ける「資産台帳」へと昇華させます。

### 2. 「なぜ（Why）」を 10 年先まで残す
「別の構成ではダメだった理由」を記録することで、将来の安易な変更による資産価値の毀損を防ぎます。

### 3. 「人間を信じない」仕組みの導入
ルールで縛るのではなく、Cloud Monitoring等による自動検知（Detection）と、IaCによる自動是正（Enforcement）を設計の前提とします。

### 4. 例外を「管理された例外」へ昇格させる
野良設定は脆弱性の温床です。すべての特例に有効期限と承認者を紐付け、ガバナンスの網から逃さない設計を行います。

### 5. IT を「負債」から「ギフト」へ
設計判断を構造化して残すことは、次世代のエンジニアへの最大のギフトです。技術負債を蓄積させない、持続可能な IT 開発文化の醸成を目指しています。
